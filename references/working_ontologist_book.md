Introduction
I first came across ontology while working on a graph-based knowledge representation for an agentic chat. The idea struck me as amazing: connect scattered ideas through semantic links, made possible by a well-curated dataset and the reasoning power of an LLM. However, the definition of ontology is not universal among the big tech companies that brand it as the next big thing, and some of that branding is probably biased. So I traced it back to its root, and Semantic Web for the Working Ontologist is widely considered a good reference.

As I read, I realized that ontology was originally built for a different purpose: to unify knowledge from multiple sources and gather it with ease, amid the chaos of “anyone can say anything.” The idea sounds great, but I am not ambitious enough to model a whole network, and I don’t feel very motivated by that goal. I am more curious about how to curate domain knowledge and formulate it into an ontology for consumption, so I mostly care about modeling a certain group of knowledge. OWL also promises the exploration of new knowledge, but I think that idea is not ready yet, if you approach it in an automatic way.

If your goal is to be practical about constructing and representing knowledge, the first five chapters are good enough. Inferencing still takes a large effort to build into your ontology, so I would only go deep on it if you are serious about learning all of the semantic modeling here.

That said, the whole book is worth a look to see how everything comes together: why the Web needs modeling, the foundations of RDF and SPARQL, inferencing, vocabulary handling with RDFS-Plus and SKOS, and OWL as the ultimate model.

Part 1. Why the Web needs modeling
Chapter 1: What is the Semantic Web
The Semantic Web aims to support a distributed Web at the level of data rather than presentation. Instead of one page linking to another, one data item points to another through global URIs, so information about a single entity can be spread across the Web yet still form one shared model. The “why” is to make the Web smarter by letting machines work with data directly, rather than leaving everything to human readers to interpret.

The challenge is the AAA Slogan: Anyone can say Anything about Any topic. Because publication is in the hands of whoever produces the content, Web data is a wilderness, valuable but tangled, and it can be contradictory, deceptive, mistaken, or outdated. This has two direct consequences. First, we must assume an open world, since there is always more that someone could say. Second, names are nonunique, since publishers don’t coordinate and the same entity can be known by many names. The Web still thrives through the network effect, where each new participant raises the value of joining for others, but that growth depends on the infrastructure coping with wide variance in the data.

The working ontologist’s job is to turn this mess into usable, durable information resources. Their medium is the distributed web of data, their tools are RDF, RDFS, SPARQL, SKOS and OWL, and their craft is modeling, which provides the structure that lets data interact in a principled way.

Chapter 2: Semantic modeling
The answer to the unconstrained Web is modeling: the process of organizing information for community use. Models are the remedy because they let people communicate a shared picture of a situation, explain and predict by relating phenomena to one another, and mediate between viewpoints by capturing what people agree on while leaving room to explore where they differ. The point worth remembering is that the standards are meant as a medium for collaborating on models, not just for sharing data.

The central problem is that structured and unstructured knowledge about the same topic will coexist on the Web at all times. Some knowledge will be well organized and expressible in a formal language, while other knowledge stays in a discordant stage where everyone describes it their own way. There is no point at which the mess is cleaned up once and for all, so the challenge is to support a continuous process of distilling communal knowledge out of this mix, without forcing agreement up front and without demanding that everyone use the same level of formality. This is where the chapter’s recurring tension between commonality and variability sits: any modeling language has to let people capture what a set of things shares while still accommodating the ways they differ.

The book’s response is a family of layered modeling languages that differ in expressivity, so people can choose the amount of formal meaning they need. RDF comes first as the basic mechanism for making simple statements and merging them into a single model. RDFS adds classes, subclasses and properties, which covers the familiar object-style notions of commonality and variability. RDFS-Plus is the book’s own pedagogical subset of OWL, in the middle, adding enough about how properties behave and relate (such as the uniqueness of a preferred symbol) to show the value of going beyond RDFS without OWL’s intimidating complexity. OWL sits at the top, bringing the expressivity of logic for detailed constraints among classes, entities and properties. The takeaway is that expressivity is a dial to be set per problem, and the rest of the book walks through each language with real-world usage.

Part 2. The foundations: RDF, architecture and SPARQL
Chapter 3: RDF, the basis of the Semantic Web
Chapter 3 introduces RDF as the foundation layer of the Semantic Web, the one that solves the problem of managing distributed data. In RDF, a resource is anything someone might want to talk about. The word is admittedly an odd choice, since alternatives like entity or thing might be more accurate but carry their own baggage, yet it is built into the name itself: Resource Description Framework. The chapter reasons from a plain table: data can be spread across servers by row, by column, or by cell, and only cell-by-cell distribution fully honors the AAA slogan, since any server can then say anything about any entity and any property. RDF takes that route, so every cell becomes a triple of subject (the row), predicate (the column) and object (the value). Because each statement stands alone, there are no columns to line up and no missing values to worry about: a relationship is either present or it is not. Seen as a directed graph, each triple is a labeled edge, and everything known about an entity gathers at a single node. The payoff is that merging data from several sources reduces to taking the union of all their triples.

The central problem is that this flexibility moves all the difficulty into identity. Cell-level distribution needs a global reference for both the rows and the columns, and merging only works if we can say when a node in one graph is the same node as in another. RDF’s compactness is the price paid for flexibility, and global identity is the one challenge left over.

RDF borrows the Web’s own solution to identity rather than inventing a new one: URIs, with namespaces (a set of names belonging to a single authority) and qnames as abbreviations for them. Two nodes are the same exactly when they share a URI, and a single triple can mix terms from several namespaces, which is how RDF supports AAA in practice. A small set of built-in terms in the rdf namespace gives a minimal typing system: rdf:type links an instance to its type, types can themselves have types, and rdf:Property marks an identifier as a predicate. Blank nodes cover the case of something that exists but has no identifier, standing in for anonymous entities that cannot be referenced globally. Examples are written in Turtle, one of several serializations alongside N-Triples and RDF/XML.

Chapter 4: Semantic Web application architecture
A Semantic Web application is built from a small set of components that fit together in a fixed order: an RDF parser and serializer, an RDF store, an RDF query engine, and application code. An RDF parser reads text in a serialization such as RDF/XML or Turtle and interprets it as triples, and an RDF serializer does the reverse, so a round trip returns the same set of triples. Converters, RDFa and microformats feed tables, spreadsheets and web pages into the same triple form. An RDF store is a database tuned for storing and retrieving triples. Its distinguishing capability is merging, the union of all and only the triples from the sources, with resources sharing a URI treated as the same, so stores are judged on merge efficiency as well as volume and speed. The RDF query engine retrieves data from the store through structured queries and depends on the store’s indices, so the two are tuned together. Early on each RDF product had its own query language, and the W3C standardized an RDF query language from their common features: SPARQL. SPARQL also includes a protocol that lets an engine act as a web service, which is what SPARQL endpoints are, including ones over data that is not natively RDF. The application does the actual work, such as analysis, user interaction or archiving, in a general-purpose language that reaches the data only through queries.

These components handle the mechanics of combining data but say nothing about meaning, so data held in RDF is not necessarily a semantic model, and the components are only the building blocks that a model needs. Meaning is supplied by semantic models, which sit in the same store as ordinary data because RDFS and OWL are built in RDF. They carry metadata that organizes the other data and acts as glue between sources.

Data federation follows from this design. Every source is converted to triples and merged into one store before any querying, so queries do not need to know where a triple came from, can span several sources at once, and are unaffected when a new source is added. Typical RDF applications built this way include calendar integration, which shows appointments from different people and teams in one view, and map integration, which places points of interest from several sites, spreadsheets and databases on a single map. Annotation lets a community apply keywords with URIs to information for others to consult, and content management builds a single index over documents, web pages and databases held in different content stores.

Chapter 5: Querying the Semantic Web with SPARQL
RDF works as a tell-and-ask system: asserting triples tells the store facts, and queries ask for answers drawn from what it was told. Like a relational database, it holds complex structured data and needs a precise, technical query language, because natural language is not a practical way to specify what you want. Unlike a relational database, the cross-references between pieces of data are not visible to the user and do not have to be spelled out in the query. SPARQL is the standard way to get at RDF. Its design is meant to be easy for SQL users to pick up, and its syntax borrows from both SQL and Turtle.

The difficulty is asking precise questions of data whose structure you may not know in advance. On the Semantic Web, you will often meet data sets whose properties and schema you have never seen, so a query language that only works when you already know the model would be of limited use. The questions people want to ask also grow as complicated as the data itself, spanning several linked entities at once, so the language needs to scale with that complexity without making the query author manage how the pieces connect.

The answer is the graph pattern: a small graph mixing known resources and variables, matched against the data graph. A question is written to look like the data it targets, with a variable standing in for whatever is unknown, and the engine finds every match and returns the values the variables bound to. Because a pattern can contain as many connected triples as needed, with shared variables tying them together, the complexity of a question is limited only by the complexity of the data. Variables can match any resource, predicates included, so the same mechanism can ask what is known about an entity, which is how you explore an unfamiliar data set and discover its properties and schema. Patterns serve two query forms. SELECT retrieves variable bindings, much like a SQL query. CONSTRUCT uses the same pattern matching to build a new graph from a template, which lets a query transform data and act as a rule. Federated queries extend this across multiple data sources in a single query.

Part 3. Meaning through inference: inferencing, RDFS and RDFS-Plus
Chapter 6: RDF and inferencing
Inferencing means that from stated information you can determine other, related information that can be treated as if it had been stated. In the Semantic Web, the meaning of a modeling term is defined by the inferences it licenses. The central example is subClassOf: if A is a subclass of B and something is of type A, then it is also of type B. This type propagation rule is the entire meaning of subClassOf in RDFS, and it behaves like an IF/THEN construct. Very simple inferences like this are usually more useful for making data connected and consistent than elaborate ones. Rules of this kind can be written as SPARQL CONSTRUCT queries, which is the notation the book uses for RDFS and OWL inferences from here on.

The problem is that federation only puts data from many sources into one store. The sources still describe things differently, so a single query cannot yet fetch related data across them. Fixing this means adding relationships to the data itself, and the terms that express them need a precise meaning that holds when data from different sources is merged. Informal definitions, as in thesauri, leave the interpretation of unforeseen combinations of terms to consensus or authoritative proclamation, and on a merged Web such combinations are bound to occur.

Defining meaning through inference patterns removes that need for decisions, because a novel combination is resolved by applying the rules together. A class that is a subclass of two classes just triggers the type propagation rule twice, so its members belong to both. Making this useful requires an inferencing capability alongside the query engine, between the application and the store, so that queries return inferred triples as well as asserted ones. The power of this engine is set by the inferences it supports.

Asserted triples are those provided by a data source; when a store is built by merging many sources, every merged triple counts as asserted. Inferred triples are those added by applying an inference rule to triples already present. They differ only in provenance: once an inferred triple exists, there is no logical distinction, and the engine draws exactly the same conclusions from it as from the same triple asserted. If a rule infers a triple that was already asserted, it still counts as asserted. Treating inference as a separate pass over the store is what makes the distinction meaningful, since it yields an original store and an augmented one.

The standards define which inferences are valid but not when they are computed. With cached inferencing, inferred triples are stored with the data, which is simple but risks an explosion of triples and makes change management hard, since removing a source triple raises the question of which inferred triples should go, given that a triple may be inferable in several ways. With just-in-time inferencing, inferences are computed at query time and never kept, which avoids that problem but repeats work. A variant does no explicit inferencing at all, with queries spelling out what they need, yet the inference reading of the model is still what explains its meaning.

The remaining languages differ only in which inference rules they include. RDFS has a small set that mostly relates classes to subclasses and properties to classes. RDFS-Plus is the book’s own extension that adds constraints on properties and notions of equality, and OWL goes further with rules that describe classes by the values their properties allow. Expressivity is therefore a choice of how much inference the model needs to support for the integration at hand.

Chapter 7: RDF schema
RDFS is the schema language for RDF, and it is itself written in RDF triples, which means schema information is as open to the AAA slogan as data is. It adds no new machinery to the language: the “keywords” (rdfs:Class, rdfs:subClassOf, rdfs:subPropertyOf, rdfs:domain, rdfs:range, rdfs:label) are ordinary resources that a standard has marked as special. Their meaning is defined entirely by inference patterns, each of the form “given this pattern of triples, add these new triples,” and not by validation or constraint. This is what separates RDFS from schemas in object modeling or XML: it describes sets and how data can flow between them, which makes it a tool for integrating differently structured sources. The upshot is that subClassOf and subPropertyOf serve as the IF/THEN facility of semantic modeling, and this role carries straight into OWL.

The problem is how to combine information from many sources when the schema language has no logical primitives. RDFS has no set intersection or union, and no direct way to say that two properties from different sources should be treated alike, yet integration constantly demands exactly these effects. A second difficulty is conceptual: domain and range are the hardest terms for newcomers because they look like OO-style declarations but never reject data. A triple that violates them just causes the subject or object to be inferred into that class, so careless use produces unintended classifications once outside data is merged in.

The solution is to get the needed logical effects from small patterns of subClassOf and subPropertyOf. A common superclass or superproperty approximates union, and a single subPropertyOf triple transfers uses of a property from one source to another. Combining these patterns lets differently named properties, such as personName and movieTitle, all map to rdfs:label. Domain and range are kept for deliberate filtering and classifying, treated as tools for knowledge discovery rather than description. Whenever you are tempted to do a global find-and-replace on merged data, use these constructs instead.

Chapter 8: RDFS-Plus
RDFS-Plus is a subset of OWL, picked as a small step up from RDFS that adds real power without a large conceptual leap. It is also the part of OWL that turns up most in practical integration projects, and it can be implemented with many different inferencing technologies, so the Semantic Web does not depend on one engine. Like RDFS, it is written in RDF with its constructs in the owl namespace, and each construct means exactly what its inference rules license. What it mainly adds is a way to handle sameness when merging data from several stakeholders who will not necessarily use the same URI for the same entity. equivalentClass and equivalentProperty align classes and properties across sources, and sameAs declares that two individuals are one. FunctionalProperty and InverseFunctionalProperty let the engine compute sameness instead of requiring it to be asserted, because a property allowing only one value identifies whatever shares that value.

Part 4. Vocabularies in the wild: RDFS-Plus and SKOS
Chapter 9: Using RDFS-Plus in the wild
Data.gov publishes government datasets, with metadata for all of them and the content of hundreds released as RDF, as raw data from many source formats that nobody prepared for any particular application. The use case is mashups: because the data is RDF, datasets can be mixed with each other or with other web data, which was far harder and costlier before the Semantic Web. SPARQL does most of the work here, since its pattern matching, aggregates, filters, subqueries and unions extract just what a report or display needs.

FOAF describes people, the groups and documents they are tied to, and their relationships, with the information about one person spread across many pages and sites. Its use case is letting individuals own and host their data while still interacting with others, as a framework that complements existing social networking systems rather than replacing them. RDFS-Plus is applied selectively and over time. Some FOAF terms are defined only in natural language, while others are formally related to the rest of the vocabulary through RDFS-Plus, so FOAF can start with a few intuitive terms and tighten their meaning as they are used. New vocabulary can then be linked to old once the intended relationship is known.

Facebook’s Open Graph Protocol (OGP) lets any web page be “liked” in Facebook, not just pages inside it. Its model is deliberately small, with about two dozen types and as many properties in a single namespace, and it is embedded in a page’s header using a simplified form of RDFa. OGP reinvents terms that FOAF and the W3C geospatial vocabulary already have, because Facebook’s content managers wanted to remember only one namespace. This is the non-unique naming assumption at work, and the model handles it by coexisting with the other vocabularies. Its terms are linked to them with rdfs:seeAlso rather than the stronger owl:equivalentProperty, which commits to less but is enough for linking. This keeps OGP connected to other systems in a machine-readable way, so it does not become another silo.

Chapter 10: SKOS, managing vocabularies with RDFS-Plus
SKOS is the W3C Recommendation for publishing controlled vocabularies, thesauri, taxonomies and folksonomies in a distributed, linkable form. It is meant to augment existing thesaurus standards, not replace them, and any of them can be mapped to SKOS fairly directly. It matters because controlled vocabularies are the best common ground for integrating information sources, and almost anything with a standard, official name can serve as one. SKOS is a model built on RDFS-Plus, and it relies on RDFS-Plus inferencing to fill out its information structure.

Vocabularies predate computers and the Web, so they were built as stand-alone systems, and until SKOS there was no standards-body recommendation for storing one digitally. SKOS fixes the linking problem by giving every concept a URI, which turns the local identifiers most thesauri already have into global ones, so terms from different vocabularies can appear in a single statement. Matching properties such as exactMatch, closeMatch, broadMatch and narrowMatch then say how a term in one vocabulary relates to a term in another, while each term stays distinct within its own source. The semantic relations (broader, narrower, related) resemble subClassOf, but the user chooses whether to treat them as transitive. Normative integrity conditions, expressed as RDFS domain and range statements or SPARQL ASK queries, check that a model conforms to the standard. Adoption comes from simplicity: any existing vocabulary that can be queried for its broader, narrower and related terms can be converted to SKOS by recording each answer as a triple.

Part 5. OWL and ontologies at work
Chapter 11: Basic OWL
OWL extends RDFS-Plus with owl:Restriction, which defines a class by describing its members in terms of classes and properties that are already modeled. Because a restriction is itself a class, it can be used to build further classes, which is how information defined by one source gets reused and extended by others. RDFS cannot do this: domain and range only make inferences about all members of a class, and nothing in RDFS lets you define a new class from existing ones. A restriction defines a class by the values its members have for a property, such as requiring a particular value, or requiring that some or all of the values come from a given class. Layering restrictions on one another lets complex relationships be modeled formally, so they can be processed automatically instead of being specified informally.

Chapter 12: Counting and sets in OWL
OWL adds a full set-theory vocabulary: unions, intersections and complements of classes, which can be applied to named classes and restrictions alike and so allow very detailed class definitions. It also adds cardinality restrictions, which define a class by how many distinct values a property has, either exactly or with a minimum or maximum. Disjointness states that two classes share no members, and OWL provides ways to declare that individuals are different from one another. Together these let a model rule things out as well as rule them in.

Counting and ruling things out are hard on the Semantic Web because new facts can always turn up, and because one thing can go by several names, so you cannot assume that two names mean two things. OWL is therefore cautious about what it concludes. The way around this is to close off a part of the world on purpose: state exactly which members a class has and that they are all different from one another, and counting and elimination then work. Beyond individuals, OWL can also reason about the classes themselves, working out how they relate without needing any data and spotting contradictions or classes that could never have members. This extends inference from the data to the model itself.

Chapter 13: Ontologies on the Web, putting it all together
Good Relations, QUDT and the OBO ontologies show OWL at work in the wild, and they span a range from almost no data (Good Relations) to very large, richly connected data (OBO). What they share is the basic Semantic Web role of giving standard entities globally unambiguous names, so information can be shared coherently across systems.

Good Relations (GR) is a small vocabulary that lets businesses describe their offerings in structured detail, so web pages can be marked up in RDFa. It is more ambitious than OGP but keeps a commitment to simplicity, and it links to existing standards such as the UN/CEFACT unit codes. Its use at tens of thousands of sites improved search ranking and let Google show richer product information, and the longer-term aim is true semantic search, where a customer can be specific and trust that a matching product can be found. The GR data itself is not in the ontology but spread across the Web. QUDT, built by NASA, addresses units of measure with three functions: a global URI for each unit, so that “pound” is unambiguous; conversion between commensurate units; and dimensional analysis, which catches errors such as adding kilograms to centimeters. It does this by keeping quantities, units and dimensions separate. It sits in the middle of the three, since it holds some data of its own but mainly connects other data sets, so two sources that both use GR can still interoperate despite different units. The OBO ontologies, such as CHEBI for chemicals, give unambiguous references to tens of thousands of biological concepts, which helps in organizing laboratory data and locating publications. They also act as a Rosetta Stone linking the many existing naming schemes for the same entities, and their detailed knowledge supports elaborate scientific searches.

Part 6. Modeling well: practices and expert OWL
Chapter 14: Good and bad modeling practices
This chapter shows how to tell a good model from a bad one by giving guidelines, then antipatterns to avoid. Under the AAA slogan none of the antipatterns are strictly errors, but each defeats the goal of sharing information with other stakeholders.

Know what you want. Start from competency questions, the questions the model must answer, and model no further than needed. They have two limits: models found on the Web rarely come with them, and a semantic model will be merged with unanticipated sources. So it must express variation as well as meet known requirements, and be built for anticipated settings beyond your own.

Say what you mean, mean what you say. Names cannot show whether a model meets its intent. “Wishful naming” gives a class a name its contents do not earn, and names are often imprecise. A model answers questions either by direct lookup of indexed data or by inferencing, and inferencing is what keeps answers consistent across questions. The test is whether the model’s inferences reflect the relationships you intended.

Model for reuse. Inference engines ignore names, but humans do not, so use insightful names and annotations (rdfs:label, rdfs:comment, rdfs:seeAlso) to make intent clear and prevent misreadings. Follow standard naming conventions.

Classes versus individuals. This is among the hardest decisions, because stakeholders may treat the same thing differently (the Class-Individual Mirror pattern handles this), and natural language blurs the two. Two guidelines:

If you cannot imagine instances of a class, it should not be a class.
If you know specific property values for a thing, it is probably an instance.
Model testing. Check the model against its competency questions. More importantly, analyze its inferences for consistency across questions from different sources, and for behavior on information outside its design.

Antipatterns

Rampant classism: Making everything a class, driven by tooling and by automatic conversion of thesauri. It reads naturally in English but breaks under inference.
Exclusivity: Assuming only known members of a superclass can belong to a subclass.
Objectification: Treating classes as object-style templates. In the Semantic Web, properties exist independently of classes, and classes are sets, so multiple membership is normal.
Creeping conceptualization: Confusing “design for reuse” with “say everything you can.” Extra concepts restrict others’ ability to extend the model. Warning sign: many empty classes with no properties, restrictions or instances. Keep it simple (KISS).
The Semantic Web assumptions (AAA, Open World, Nonunique Naming) define what the modeling languages mean, so a good model is one whose inferences are useful and meaningful. Some mismatches, like objectification, come from requirements that clash with those assumptions. Others, like exclusivity, are consistent with them and fixable with a simple pattern.

Chapter 15: Expert modeling in OWL
OWL comes in subsets because people build models for two different reasons, and each reason needs a slightly different version of the language.

Why subsets exist. Think of OWL as one toolbox. Every subset contains the same tools, and each tool means the same thing everywhere. What differs is the rules about how you may use them. A stricter subset gives you stronger guarantees, and a looser one gives you more freedom. The right choice depends on what you want from your model.

Two reasons to model. Some people want a model to be provable: precise enough that a computer can always work out, in finite time, whether two sources mean the same thing (does your “James Dean movie” match mine?). The catch is that logic powerful enough to be useful often cannot guarantee an answer, so the guaranteed version has to be carefully restricted. Others treat a model like a small program that merges and reshapes data from many sources. Programs cannot be proven correct in general either, yet they work, because engineers test and fix them until they behave on the data that matters. This second group accepts “good answers most of the time”, which suits messy Web data and lets many more tools process the model. The subsets exist to serve each camp.

The four profiles. OWL 2 offers four named subsets, called profiles. OWL 2 DL is the most expressive version that still keeps the guarantee of provable answers. OWL 2 QL is for applications that sit on top of ordinary databases. OWL 2 EL is for very large ontologies, such as those in life sciences. OWL 2 RL is for rule-based software. Since they share the same vocabulary, a model written in one can be read in another.

New in OWL 2. Three additions make modeling more flexible:

Treating a class as a thing in its own right. The same concept can be a category in one context and an individual item in another (an eagle species can be listed as endangered, or counted as a group of birds). OWL 2 lets one name play both roles, but the book advises against this and recommends keeping the two separate and stating how they relate.
Chaining relationships. A new relationship can be built from a sequence of existing ones. “Uncle” is “brother of a parent”.
Identifying things by several details together. Two records with the same name and the same address are likely the same person, much like a multi-column key in a database. OWL still cannot say “probably the same”, only “the same”.
Rules. A rule is a simple “if this is true, then conclude that” statement, so a rule-based model is a list of such statements applied to the data. Rules can fill OWL’s remaining gaps, including chaining relationships, identifying things by several details, and even handling uncertainty. So why not use rules for everything? Experience shows that large rule-based systems are harder to build and maintain well, and unrestricted rules cannot be guaranteed to give answers any more than ordinary programs can. The practical answer is to combine the two, which is what OWL 2 RL and the Rule Interchange Format (RIF), the Web standard for sharing rules, do.

Takeaway. OWL keeps growing through new features, links to other technologies like rules, and named subsets. The right choice depends on whether you need provable correctness or practical, efficient data integration.

Part 7. Conclusions
Chapter 16: Conclusions
Veterans of knowledge modeling often call the Semantic Web “same old, same old”, since classes, subclasses and properties are decades old. What is new is the World Wide Web itself: the Semantic Web is not an application running on the Web but part of its infrastructure. Like the Web, it wins by being open and drawing on information from many sources, so a primitive language like OWL can still deliver real results. People want access to information so they can perform like experts, and the Semantic Web gathers information scattered across places so users don’t have to integrate it by hand.

It does this by borrowing the Web’s own design. Because every reference on the Web is global, URIs let separately built models merge simply by mentioning resources from both in one statement. Because the Web is open and tolerates broken or incorrect content, the Semantic Web must as well, so inferencing is conservative under the Open World assumption. This also handles scale: no store can hold the whole Web, and none needs to, since an application only has to access and merge any page, not all of them. The craft of Semantic Web modeling is combining RDF, RDFS and OWL into a system through which this data can flow.
